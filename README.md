# STSTATS

스타 방송을 하는 스트리머들의 통계를 자동으로 모아서 보여주는 프로젝트입니다.
2026년 7월부터, `data/members.json`에 등록된 스트리머 전원(활동 팀 소속 + FA/휴면 포함)의

- **별풍선 / 방송시간 / 누적시청자** — 풍고(poonggo.com) 공식 API에서 자동 수집
- **스폰전적(스폰판수)** — EloBoard(eloboard.co.kr) 공식 API에서 자동 수집

를 모아서, 세 종류의 페이지로 보여줍니다. 날짜/지표 드롭다운으로 즉시 전환되며, 페이지 이동
(새로고침)이 없습니다. 화면에 그리는 작업은 전부 브라우저 자바스크립트가 하고(클라이언트
렌더링), 파이썬 스크립트는 매일 최신 데이터를 JSON으로만 만들어둡니다.

## 페이지 3종류

| 페이지 | 경로 | 내용 |
|---|---|---|
| 전체 페이지 | `docs/index.html` | 모든 팀 비교 그리드 + FA 명단 |
| 팀별 페이지 | `docs/team.html?team=팀이름` | 팀 하나만 떼서 보는 화면 |
| 개인 프로필 | `docs/profile.html?id=SOOP아이디` | 파일 하나로 전 인원 대응 - 성별/생년월일/소속/직책/종족/티어/방송국/지표 4개 |

## 데이터 소스 두 곳

1. **풍고(poonggo.com)** — 정식 이용 허가를 받아 사용 중인 공식 API (`/api/monthly`). 별풍선/방송시간/누적시청자를 API 호출 1번으로 모두 얻습니다. `fetch_poonggo_data.py`가 담당합니다.
2. **EloBoard(eloboard.co.kr)** — 스폰전적(승/패). 공식 API(`/api/matches`)를 `player_id`(=`members.json`의 `elo_id`) 기준으로 페이지네이션하며 조회합니다. `fetch_eloboard_data.py`가 담당합니다.

두 스크립트 모두 HTTP 요청은 `_common.fetch_json()`을 거칩니다 - 타임아웃(30초)과 재시도(최대 3회, 3초 간격 백오프)가 여기 한 곳에서 통일되어 있어서, 일시적인 네트워크 오류 하나 때문에 그 실행에서 수집한 데이터가 조용히 반쪽만 저장되는 일이 없습니다(재시도를 다 소진하면 예외 대신 실패를 명확히 알리고, 호출부는 기존 값을 그대로 유지합니다).

`fetch_poonggo_data.py`와 `fetch_eloboard_data.py`는 **각자 데이터를 가져오기만 하는
순수 함수**입니다 - `data/latest.json`을 언제 쓸지, 아카이브를 언제 만들지는 전혀
모릅니다. 그 조율은 전부 `update_data.py` 하나가 담당합니다:

1. 날짜가 바뀌었으면 어제자 스냅샷을 아카이브로 확정
2. 달이 바뀌었으면 지난달 마지막 날 아카이브에 별풍선(풍고 재조회)과 스폰전적
   (엘로보드 재조회)을 **둘 다** 확정 적용
3. `info_updated_at` 소급 정정 적용
4. 오늘자 별풍선/스폰전적을 새로 가져와서 하나로 합쳐 `latest.json`에 저장

원래는 두 스크립트가 각자 독립적으로 `latest.json`을 읽고 쓰다 보니, 어느 스크립트가
먼저 도는지에 따라 "아카이브 파일이 아직 없어서 확정을 못 함" 같은 순서에 민감한
버그가 계속 생겼습니다. 지금은 한 곳에서만 판단하므로 그런 문제 자체가 생길 수
없습니다. 엘로보드 쪽 API 호출이 실패해도(재시도까지 다 소진한 경우) `update_data.py`가
내부적으로 예외를 잡아 기존 스폰전적을 보존하고 별풍선 데이터는 정상적으로 저장합니다
- 워크플로우 자체가 실패하지 않습니다.

## 하루 단위로 데이터가 쌓입니다

`update_data.py`는 실행될 때마다 오늘 날짜 기준으로 `data/latest.json`을 갱신하고,
**날짜가 바뀐 걸 감지하면** 어제자 스냅샷을 `data/archive/YYYY-MM-DD.json`으로 보관합니다.
**성별/생일**은 안 바뀌는 정보라 이 스냅샷들엔 아예 안 들어가고 `members.json`에서만
관리되며, 페이지를 그릴 때 그때그때 조회해서 씁니다.

**달이 바뀌는 시점**(예: 8월 마지막 날 → 9월 1일 첫 실행)에는, 그냥 복사만 하지 않고
**별풍선(풍고 API)과 스폰전적(엘로보드 기간검색) 둘 다 8월 기준으로 한 번 더 재조회**해
확정된 값으로 갱신한 뒤 그 날짜로 보관합니다(두 데이터 모두 월말 이후 뒤늦게 갱신될
가능성에 대비 - 예를 들어 8월 마지막 날 자정 직전에 발생한 스폰전적도, 재조회 시점엔
eloboard.com에 반영돼있을 테니 놓치지 않고 잡힙니다). 이 확정은 달이 바뀐 **첫 실행에서
바로** 일어납니다 - 아카이빙과 월 확정이 같은 스크립트 안에서 순서대로 처리되므로,
"아카이브 파일이 아직 없어서 확정을 못 하고 다음 실행까지 미뤄지는" 상황이 생기지
않습니다.

## 팀/직책/종족/티어를 나중에 고치면 - `info_updated_at`

`members.json`에서 어떤 사람의 `team`/`role`/`race`/`tier`/`nickname`을 고치고
`info_updated_at`에 **오늘 날짜("YYYY-MM-DD")**를 넣으면, 다음 자동 실행 때
**그 날짜 이후의 모든 일별 아카이브**에 새 값이 자동으로 소급 적용됩니다. 예를 들어
어떤 사람이 사실 지난주부터 다른 팀이었다는 걸 뒤늦게 알았다면, `info_updated_at`을
그 날짜로 넣어두면 이미 만들어진 지난 며칠치 기록까지 알아서 고쳐집니다.

한 번 소급 적용이 끝났다고 판단되면(보통 하루 이틀 뒤), `info_updated_at`을 다시
비워두는 걸 권장합니다 - 계속 남겨두면 그 날짜 이후로 쌓이는 아카이브가 늘어날수록
매번 검사해야 할 파일 수도 같이 늘어납니다(안전하지만 조금씩 느려짐).

## 팀별 순위와 전달 대비 변동

각 팀은 지표별 평균 기준으로 정렬되고(스폰판수만 여자 평균 기준, 나머지는 전체 평균 기준),
팀 이름 옆에 전달 대비 순위 변동이 표시됩니다(▲상승 / ▼하락 / - 동일 / NEW 신규 - 전체
페이지에서만, 팀 단독 페이지엔 표시 안 함). "전달"은 지금 보고 있는 날짜의 전달 중
**가장 최근 날짜**를 기준으로 비교합니다(일별 아카이브라 특정 하루를 콕 집어 비교할 수
없어서, 그 달의 마지막 스냅샷 = 최종 확정치를 씁니다). 비교할 전달 데이터가 없으면
표시되지 않습니다.

## FA 명단 (전체 페이지 하단)

`team`이 `FA`인 사람들을 모아서 전체 페이지 맨 아래 카드에 보여줍니다(팀 단독 페이지엔
안 나옵니다). 기본은 접힌 상태로 시작하고, 눌러서 펼치면 사진+닉네임이 티어 순서
(갓 → 킹 → 잭 → 조커 → 스페이드 → 0~8 → 유스)로 정렬돼 나옵니다. 목록에 없는
티어 값(빈 값 등)은 맨 뒤로 갑니다.

## 팀 로고 (`docs/logos/`)

`docs/logos/{팀이름}.webp` 파일이 있으면 표 상단 팀 이름 옆에 자동으로 로고가 붙고, 그
로고 색상을 뽑아 팀 카드/개인 프로필 상단 바 색으로도 씁니다. 파일명은 `members.json`의
`team` 값과 정확히 일치해야 합니다. 파일이 없는 팀은 그냥 텍스트만 표시되며 오류가 나지
않습니다. `FA`/`휴면`은 애초에 팀이 아니라서, 개인 프로필 상단 바가 자동으로 회색 고정됩니다.

## 모바일 화면

전체 페이지(팀 비교 그리드)는 좁은 화면에서 2열로 압축되면서 글자 크기 등이 줄어듭니다.
반대로 **개인 프로필/팀 단독 페이지는 원래부터 1열 레이아웃이라 좁은 화면에서도 공간
다툼이 없어서, 데스크톱 크기 그대로 유지**됩니다(억지로 줄이면 오히려 안 읽혀서).

## 멤버 관리 어드민 페이지 (`docs/admin.html`)

`data/members.json`을 텍스트 에디터로 직접 고치는 대신, 브라우저에서 표로 보면서
검색·추가·수정·삭제하고 바로 커밋까지 할 수 있는 페이지입니다.

1. `https://ststats.github.io/ststats/admin.html` 접속
2. **"repo" 권한만 있는** GitHub Personal Access Token 발급받아 맨 위 칸에 입력 → **토큰 저장**
   (이 탭에서만 기억되고, 레포에는 저장되지 않습니다)
3. **불러오기** → 검색으로 찾거나 표에서 셀 직접 수정(아이디/엘로ID/닉네임/성별/생일/
   직책/팀/종족/티어/수정일) / **+ 새 멤버 추가** / 행별 **삭제**
4. **저장** → `members.json`만 커밋하고 끝(워크플로우는 안 돌림, 여러 건 나눠서
   수정할 때 유용)
5. **저장 + 워크플로우 실행** → `members.json`이 커밋되고 `update-stats.yml`이
   즉시 트리거되어 몇 분 안에 사이트에 반영됩니다.

`OWNER`/`REPO`/`BRANCH` 값은 `admin.html` 코드 맨 위에 상수로 있습니다 - 저장소를 옮기거나
기본 브랜치가 `main`이 아니면 그 값만 고치면 됩니다.

## 멤버 관리 (인원이 바뀔 때)

`data/members.json`은 flat 구조입니다. 멤버 한 명이 배열의 항목 하나이고,
그 안에 `team` 필드로 소속을 표시합니다.

```json
{
  "members": [
    {
      "id": "SOOP(구 아프리카TV) 아이디 - 풍고(poonggo.com) 조회용",
      "elo_id": "EloBoard 사이트의 player_id(숫자) - 스폰전적 조회용, 모르면 null",
      "nickname": "표시할 닉네임",
      "gender": "m 또는 f",
      "birthdate": "YYYY-MM-DD (모르면 null)",
      "role": "수장 / 전력외 (없으면 이 줄 자체를 생략 가능)",
      "team": "소속 팀 이름 (또는 FA / 휴면)",
      "race": "종족 (테란/프로토스/저그, 모르면 null)",
      "tier": "티어 - 갓/킹/잭/조커/스페이드/0~8/유스 (모르면 null)",
      "info_updated_at": "이 정보를 마지막으로 고친 날짜 (\"YYYY-MM-DD\", 없으면 null)"
    }
  ]
}
```

- `id`는 SOOP(구 아프리카TV) 아이디입니다.
- `elo_id`는 EloBoard 사이트에서 그 사람에게 매겨진 고유 숫자 ID입니다 - 없으면(`null`이면)
  스폰전적 매칭 대상에서 자연히 빠지고 별풍선/방송시간/누적시청자는 정상 수집됩니다.
- `role`이 `수장` 또는 `전력외`인 사람은 표에서 빨간 배경으로 표시되고, 별풍선/방송시간/누적시청자/스폰판수 집계에서 모두 제외됩니다.
- `team`이 `FA` 또는 `휴면`인 사람은 데이터(풍고/ELO)는 똑같이 수집되지만, 팀 카드/팀 페이지 집계·표시 대상에선 제외됩니다(`FA`는 대신 전체 페이지 하단 FA 명단에 나옵니다). 개인 프로필 페이지에서는 정상 조회됩니다.
- `info_updated_at`을 오늘 날짜로 넣으면 그 날짜 이후 아카이브에 team/role/race/tier/nickname/elo_id가 소급 적용됩니다. 자세한 내용은 위 "팀/직책/종족/티어를 나중에 고치면" 참고.
- 새로 추가된 사람/팀은 전체 페이지·팀 페이지에 **자동으로** 반영됩니다.
- `birthdate`는 이름 옆 🎂 표시에 쓰입니다. 모르면 `null`.
- 아직 확인 못 한 값이 있으면 `null`로 비워두는 걸 권장합니다. `"체크"`, `"TODO"`, `"?"`, `"미정"`
  같은 임시 표시 문자열을 넣어도 사이트에는 자동으로 "-"(빈 값)로 처리되어 안전하게 나가지만,
  나중에 실제 값으로 채워 넣는 걸 잊기 쉬우니 가능하면 `null`을 쓰세요.
- 수정 후 GitHub에 커밋/푸시하면 다음 자동 실행(또는 수동 실행) 때부터 반영됩니다.


## 엘로보드 스폰전적 수집 방식

`fetch_eloboard_data.py`는 EloBoard 공식 API(`https://eloboard.co.kr/api/matches`)를
`limit`/`offset`으로 페이지네이션하며 호출합니다:

1. 한 페이지(최대 200건)를 가져와서, 각 경기(`match`)의 `played_on` 날짜를 조회 기간과 비교
2. 조회 기간보다 최신 경기는 건너뛰고, 기간 안에 들어오는 경기는 각 참가자(`participants`)의
   `player_id`(=`elo_id`)별로 판수/승/패를 누적 집계
3. 조회 기간보다 오래된 경기에 도달하면 더 볼 필요가 없으므로 그 자리에서 탐색 종료

API가 최신 → 과거 순으로 정렬해서 응답한다고 가정합니다. 페이지 요청이 실패하면
`_common.fetch_json()`이 자동으로 재시도하고, 그래도 실패하면 지금까지 모은 데이터가
불완전하다는 뜻이므로 부분 데이터를 저장하는 대신 빈 결과를 반환해 `update_data.py`가
기존 값을 유지하도록 합니다.

## 안정성 관련 안전장치

여러 소스(xlsx/EloBoard API/admin.html)가 같은 파일들을 건드릴 수 있는 구조라,
아래 안전장치들을 공용으로 넣어뒀습니다:

- **원자적 쓰기** (`_common.atomic_write_json`, `.xlsx` 저장용 동일 패턴) —
  `members.json`/`latest.json`/아카이브/`.xlsx` 전부 직접 쓰지 않고, 임시 파일에
  먼저 다 쓴 다음 `os.replace()`로 한 번에 바꿔치기합니다. 워크플로우가 쓰는
  도중에 죽어도(타임아웃, 강제취소 등) 원본 파일은 쓰기 시작 전 상태 그대로
  안전하게 남습니다.
- **안전한 읽기** (`_common.safe_read_json`) — 스냅샷 파일이 없거나 깨져있어도
  예외를 던지는 대신 기본값으로 대체하고 경고만 남깁니다. 실수로 지워지거나
  손상된 상태 파일 하나 때문에 전체 파이프라인이 계속 실패하는 일을 막습니다.
- **멤버 스키마 검증** (`_common.validate_and_clean_members`) — `id`/`nickname`이
  없는 레코드는 제외하고, `id`는 문자열로, `elo_id`는 정수로 강제 변환합니다.
  `update_data.py`/`sync_members.py`/`convert_members_xlsx.py`가 `members.json`을
  읽을 때마다 거쳐가서, 레코드 하나가 이상해도 나머지 전원의 그날 데이터 갱신이
  통째로 죽지 않습니다.
- **엘로보드 페이지네이션 상한선** (`fetch_eloboard_data.MAX_PAGES`) — API 정렬
  가정이 깨지는 등의 이유로 종료 조건에 영영 도달 못 하면, 무한정 도는 대신
  일정 페이지 수에서 실패로 처리하고 끝냅니다(그래야 워크플로우 전체 시간을
  다 잡아먹고 그날 아무 것도 못 하는 최악의 상황을 막습니다).

## 내부 동기화 상태 파일

`data/` 안에 사람이 직접 안 건드리는 자동 생성 파일이 두 개 있습니다 - 지워도 다음
실행에서 다시 만들어지지만, 지우면 아래 설명한 최적화가 그 시점부터 다시 시작됩니다
(데이터가 틀어지진 않고, 그냥 한 번 더 전체를 훑게 될 뿐입니다).

- **`data/members_sync_baseline.json`** — `convert_members_xlsx.py`가 xlsx↔json을
  양방향 동기화할 때 쓰는 스냅샷입니다. xlsx와 json 둘 다 사람이 고칠 수 있어서,
  "지난번 동기화 직후엔 이 사람 정보가 이랬다"를 기억해뒀다가 이번 실행에서 어느
  쪽이 그 사이에 바뀌었는지 판단하는 데 씁니다(3-way 병합). 이 파일이 없으면
  처음 한 번은 xlsx가 무조건 기준이 됩니다.
- **`data/archive_corrections_applied.json`** — `update_data.py`가 `info_updated_at`
  소급 정정을 아카이브에 반영할 때, "이 사람의 이 보정 내용은 이미 다 반영해뒀다"를
  기억해두는 파일입니다. 이게 없으면 소급 정정이 한 번이라도 걸린 사람이 생길 때마다
  매 실행마다 그 날짜 이후 아카이브 전체를 다시 훑게 되는데(아카이브는 계속 쌓이므로
  실행 시간이 계속 늘어남), 이 스냅샷 덕분에 실제로 새로 바뀐 보정 건에 대해서만
  다시 훑습니다.
- **`docs/data/dates.js`** — 사이트가 브라우저에서 날짜 선택 UI를 그릴 때 쓰는
  전체 날짜 목록(`window.AVAILABLE_DATES = [...]`)만 담은 작은 파일입니다. 이걸
  `index.html`/`team.html`/`profile.html` 안에 직접 박아넣지 않고 `<script src>`로
  동기 로드하게 분리해뒀습니다 - 안 그러면 매일 날짜가 하나씩 늘어날 때마다 CSS/JS
  다 포함된 큰 HTML 3개(각 45~50KB급) 전체가 매일 다시 커밋돼서, 실제로 바뀐 것도
  없이 레포 용량만 계속 불어납니다. `_write_if_changed`가 이제 이 세 HTML 파일에도
  적용돼있어서, 로스터/디자인이 실제로 안 바뀐 날은 커밋 자체가 안 생깁니다.

## 테스트

`tests/`에 두 종류의 pytest 테스트가 있습니다:
- **단위 테스트** (`test_common.py`, `test_convert_members_xlsx.py`, `test_sync_members.py`,
  `test_update_data.py`) — 까다로운 순수 로직(날짜/문자열 정규화, 티어 라벨 변환,
  xlsx↔json 3-way 병합 충돌 판단, 소급 정정 스킵 로직 등) 하나하나를 검증합니다.
- **통합 테스트** (`test_update_data_integration.py`, `test_convert_members_xlsx_integration.py`)
  — 임시 디렉터리에 실제 파일을 만들어두고 `main()` 전체를 그대로 돌려서, 여러
  함수가 실제로 올바르게 엮여 도는지 확인합니다(예: "admin.html에서 json을 고치면
  다음 실행에서 xlsx에도 반영되는지"처럼 여러 컴포넌트가 맞물려야 검증되는 시나리오).

push/PR마다 `.github/workflows/tests.yml`이 자동으로 돌립니다. 로컬에서 직접
돌리려면:

```
pip install -r requirements.txt pytest
pytest
```

## 참고

- 풍고 데이터 출처: 풍고(poonggo.com) 공식 API (`/api/monthly`, ids 파라미터로 최대 300명씩 일괄 조회 가능,
  응답에 별풍선(`amt`)과 방송시간(`broadTime`, 초)이 함께 들어있어 API 호출 1번으로 두 지표를 모두 얻음 -
  사전에 이용 허가를 받아 사용 중)
- 별풍선/방송시간/누적시청자/스폰판수 모두 값이 0이거나 직책이 수장/전력외인 멤버는 팀 합계·평균·상위 1%/5%/10% 계산에서 제외됩니다.
- 실행 시각은 GitHub 자체 스케줄(`schedule:`)이 아니라 **외부 스케줄러(cron-job.org 등)가
  정확한 시각에 `workflow_dispatch`를 GitHub API로 직접 호출**하는 방식입니다. GitHub의
  자체 스케줄러는 "최선을 다하지만 정시 보장은 안 함"이라 정시성이 중요하면 믿을 수
  없어서(공식 문서에도 명시), 이 방식으로 대체했습니다.
- `update_data.py`는 실행되는 순간의 실제 KST를 기준으로 날짜를 판단하므로, 실행이
  몇 분~몇십 분 밀려도 안전합니다(통째로 하루를 건너뛸 정도로 심하게 밀리는 경우만 예외).
